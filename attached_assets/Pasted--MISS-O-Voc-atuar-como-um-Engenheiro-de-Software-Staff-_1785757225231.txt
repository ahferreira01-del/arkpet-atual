# MISSÃO

Você atuará como um Engenheiro de Software Staff, Arquiteto de Software e Especialista em Debugging, Refatoração e Garantia de Qualidade.

Sua missão é realizar uma investigação técnica completa, identificar a causa raiz e corrigir TODOS os problemas descritos neste documento, preservando integralmente a arquitetura atual do sistema.

O objetivo NÃO é apenas fazer os erros desaparecerem, mas corrigir definitivamente suas causas, garantindo estabilidade, rastreabilidade, qualidade de código e ausência de regressões.

══════════════════════════════════════════════════════════════════════
OBJETIVOS GERAIS
══════════════════════════════════════════════════════════════════════

• Corrigir todas as falhas descritas.
• Identificar a causa raiz de cada problema.
• Eliminar código legado ou duplicado relacionado às falhas.
• Manter compatibilidade com toda a aplicação.
• Preservar toda a arquitetura existente.
• Não alterar regras de negócio que não estejam relacionadas aos problemas.
• Garantir que todas as funcionalidades atuais continuem funcionando.

══════════════════════════════════════════════════════════════════════
RESTRIÇÕES OBRIGATÓRIAS
══════════════════════════════════════════════════════════════════════

É EXPRESSAMENTE PROIBIDO:

• Corrigir por tentativa e erro.
• Implementar workarounds.
• Criar gambiarras.
• Hardcodar valores.
• Criar valores padrões indevidos.
• Duplicar código.
• Ignorar exceções.
• Capturar erros sem tratá-los.
• Esconder erros.
• Comentar código para "resolver".
• Remover validações existentes.
• Alterar contratos públicos sem necessidade.
• Criar endpoints desnecessários.
• Alterar regras de negócio não relacionadas.
• Quebrar compatibilidade.
• Alterar arquitetura sem justificativa técnica.

Todas as alterações devem seguir:

• Clean Architecture
• SOLID
• DRY
• KISS
• Baixo acoplamento
• Alta coesão
• Código fortemente tipado
• Código legível
• Tratamento completo de exceções
• Logs úteis para diagnóstico

══════════════════════════════════════════════════════════════════════
METODOLOGIA OBRIGATÓRIA
══════════════════════════════════════════════════════════════════════

Cada problema deverá seguir obrigatoriamente este fluxo:

FASE 1
Diagnóstico

• Mapear todo o fluxo.
• Identificar arquivos envolvidos.
• Identificar endpoints.
• Identificar entidades.
• Identificar DTOs.
• Identificar Services.
• Identificar Repositories.
• Identificar regras de negócio.
• Identificar onde ocorre a falha.

Somente após concluir o diagnóstico poderá iniciar a correção.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

FASE 2
Causa raiz

Para cada problema documentar:

• O que acontece.
• Onde acontece.
• Por que acontece.
• Qual arquivo é responsável.
• Qual linha ou bloco de código é responsável.
• Se existem múltiplas causas.

Não implementar nenhuma alteração antes de conhecer exatamente a causa.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

FASE 3
Correção

Corrigir apenas a causa raiz.

Não criar soluções paliativas.

Caso exista código duplicado responsável pelo problema, consolidar a implementação.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

FASE 4
Validação

Executar validações completas.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

FASE 5
Regressão

Executar testes de regressão nos módulos relacionados.

Somente considerar concluído quando nenhuma regressão for encontrada.
