MISSÃO

Implementar suporte completo para RESERVAS COM MÚLTIPLOS SERVIÇOS no sistema.

NÃO é permitido criar soluções paliativas.

NÃO é permitido adicionar IFs espalhados pelo sistema.

NÃO é permitido duplicar regras existentes.

Toda alteração deve seguir exatamente a arquitetura do domínio já existente.

O sistema financeiro foi recentemente refatorado e possui:

- BillingService como única autoridade de faturamento
- CreditService como única autoridade de créditos
- InvoiceStateMachine
- Snapshot histórico em invoice_items
- Idempotência
- Auditoria
- Locks
- Transações atômicas

A implementação DEVE respeitar tudo isso.

====================================================
OBJETIVO FUNCIONAL
====================================================

Hoje uma reserva possui apenas um serviço.

Desejo permitir:

Serviço Primário

+

N serviços adicionais (add-ons)

Exemplo

Reserva

Primário:
• Day Use

Serviços adicionais:

• Banho

• Táxi

• Escovação

Todos pertencem à MESMA reserva.

O tipo primário continua sendo o dono da reserva.

Os adicionais apenas complementam.

Jamais podem alterar a máquina de estados.

====================================================
CRITÉRIOS DE ACEITE
====================================================

A implementação será considerada concluída apenas se:

✓ Nenhuma funcionalidade existente quebrar.

✓ Nenhuma assinatura pública mudar.

✓ Nenhum endpoint existente deixar de funcionar.

✓ Toda lógica financeira continuar centralizada em BillingService.

✓ Toda lógica de créditos continuar centralizada em CreditService.

✓ Nenhum código duplicado for criado.

✓ Nenhuma regra depender de strings.

✓ Toda decisão utilizar catalogueItemId.

✓ Toda operação crítica utilizar transação.

✓ Todo fluxo for idempotente.

✓ Todo fluxo gerar auditoria.

✓ O sistema permanecer coerente com DDD.

Antes de escrever qualquer código, realizar uma auditoria completa dos impactos em backend, frontend, banco, serviços, eventos, contratos, testes e documentação.

Caso qualquer alteração possa quebrar um módulo existente, interromper a implementação e propor uma solução arquitetural melhor antes de continuar.

O objetivo NÃO é apenas implementar multi-serviços.

O objetivo é fazer essa funcionalidade parecer que sempre fez parte da arquitetura do sistema.
