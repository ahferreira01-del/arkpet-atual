# FASE 0 — GOVERNANÇA DO DOMÍNIO FINANCEIRO

## PAPEL

Você atuará como um **Arquiteto de Software Sênior**, especializado em sistemas financeiros SaaS, Domain-Driven Design (DDD), Event-Driven Architecture, sistemas transacionais e aplicações multi-tenant.

Sua missão NÃO é corrigir bugs.

Sua missão NÃO é refatorar código.

Sua missão NÃO é otimizar performance.

Sua missão é estabelecer uma **fonte única de verdade (Single Source of Truth)** para todo o módulo financeiro.

É PROIBIDO:

* alterar regras de negócio;
* alterar comportamento do sistema;
* alterar endpoints;
* alterar contratos da API;
* alterar banco de dados;

Todo o trabalho desta fase deve ser **100% documental**.

# ETAPA 2 — RESPONSABILIDADE DOS MÓDULOS

Documentar exatamente o que cada módulo pode e não pode fazer.

Exemplo esperado:

## OrderService

Pode:

* criar pedidos;
* atualizar status do pedido.

Não pode:

* liberar créditos;
* criar transações financeiras;
* consumir créditos.

---

## BillingService

Pode:

* criar invoices;
* adicionar charges;
* receber pagamentos;
* cancelar invoices;
* refund.

Não pode:

* consumir créditos;
* alterar bookings.

---

## CreditService

Pode:

* liberar créditos;
* consumir créditos;
* restaurar créditos;
* consultar saldo.

Não pode:

* criar invoices;
* criar pedidos;
* atualizar pagamentos.

---

## WalletService

Pode:

* agregar créditos;
* calcular saldo;
* listar histórico.

Não pode:

* alterar invoices;
* alterar pedidos.

---

## BookingService

Pode:

* solicitar consumo;
* solicitar restauração.

Não pode:

* atualizar diretamente tutor_credits;
* atualizar tutor_service_credits.

# ETAPA 7 — INVARIANTES DO DOMÍNIO

Definir regras que nunca podem ser quebradas.

Exemplos:

Uma invoice paga nunca pode voltar para pending.

Uma transaction sempre pertence a uma invoice.

Um crédito nunca pode ficar negativo.

usedCredits nunca pode ser maior que totalCredits.

Toda invoice paga deve possuir transaction.

Toda transaction deve possuir invoice.

Todo crédito liberado deve possuir origem.

Toda restauração deve possuir consumo anterior.

Nenhuma operação financeira pode ficar parcialmente aplicada.

Adicionar todas as invariantes encontradas.
