# MISSÃO — IMPLEMENTAÇÃO ARQUITETURAL DE RESERVAS COM MULTI-SERVIÇOS

## CONTEXTO

Este projeto já passou por uma grande refatoração arquitetural do módulo financeiro.

A arquitetura atual possui:

- BillingService como única autoridade de faturamento.
- CreditService como única autoridade sobre créditos.
- InvoiceStateMachine como única máquina de estados das invoices.
- Snapshot histórico em invoice_items.
- Idempotência em operações críticas.
- Auditoria centralizada.
- Eventos via Outbox.
- Transações atômicas.
- Separação clara entre domínios.

A nova funcionalidade deve seguir exatamente essa arquitetura.

NÃO quero adaptações rápidas.

NÃO quero código duplicado.

NÃO quero lógica espalhada.

NÃO quero ifs especiais para "multi-serviço".

Quero que essa funcionalidade pareça que sempre existiu dentro do sistema.

--------------------------------------------------

# OBJETIVO

Permitir que uma reserva possua:

• 1 Serviço Primário

e

• N Serviços Adicionais (Add-ons)

Exemplo:

Reserva

Serviço Primário
- Day Use

Serviços adicionais

- Banho
- Táxi
- Escovação
- Adestramento

Todos pertencem à MESMA reserva.

O serviço primário continua sendo o dono da reserva.

Os adicionais apenas complementam.

Jamais podem alterar a máquina de estados.

# FASE 3 — FONTE ÚNICA DE VERDADE

Eliminar definitivamente dependência de strings.

Hoje existe:

booking.type

Isso deve permanecer apenas para compatibilidade.

Adicionar:

primaryCatalogueItemId

na tabela bookings.

Reservas antigas:

primaryCatalogueItemId = NULL

Reservas novas:

primaryCatalogueItemId preenchido.

A partir desta implementação:

catalogueItemId passa a ser a única fonte oficial de identificação de serviços.

Novas regras jamais poderão depender de:

booking.type

regex

nomes

descrições

Toda lógica utilizará catalogueItemId.

# CRITÉRIOS DE ACEITE

A implementação somente será considerada concluída se:

✓ Nenhuma funcionalidade existente quebrar.

✓ Nenhum endpoint existente deixar de funcionar.

✓ Nenhuma assinatura pública mudar.

✓ Clientes antigos continuarem funcionando.

✓ Todo faturamento continuar centralizado em BillingService.

✓ Todo crédito continuar centralizado em CreditService.

✓ Todo serviço seja identificado exclusivamente por catalogueItemId.

✓ booking.type permaneça apenas para compatibilidade.

✓ Nenhuma regra utilize strings ou regex.

✓ Toda operação crítica seja transacional.

✓ Todo fluxo seja idempotente.

✓ Todo fluxo gere auditoria.

✓ Toda reserva seja tratada como um Aggregate.

✓ Nenhum código duplicado seja criado.

✓ Nenhuma lógica financeira seja espalhada pelo sistema.

✓ Nenhum remendo seja introduzido.

## INSTRUÇÃO FINAL

Antes de implementar qualquer alteração, realizar uma auditoria completa dos impactos e apresentar um plano técnico detalhado.

Caso qualquer decisão possa comprometer a arquitetura existente, interromper a implementação e propor uma alternativa arquitetural mais adequada antes de modificar o código.

O objetivo não é apenas adicionar múltiplos serviços em uma reserva.

O objetivo é evoluir definitivamente o domínio de reservas, mantendo a mesma qualidade arquitetural já existente no módulo financeiro.
